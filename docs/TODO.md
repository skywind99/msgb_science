### AI 키·호출 설계 (확정)

**이전의 환경변수 `GEMINI_API_KEY` 방식은 폐기했다.** 공급자가 둘로 늘고 관리자가
화면에서 키를 갈아끼울 수 있어야 해서 DB 보관으로 바꿨다.

**키의 주인은 사람이 아니라 사이트다.** 누가 AI 버튼을 눌러도 서버가 같은 키 세트
(Groq, Gemini)를 쓴다. 교사별 키는 없다.

저장
- 설정 테이블 **한 행**. 공급자별 키를 **AES-256-GCM** 으로 암호화해 저장하고
  복호화는 서버에서만 한다.
- 비밀값은 환경변수 **`AI_KEY_SECRET`**.
- **키가 로그·응답·에러 메시지에 나오지 않게 한다.**

권한
- 키 등록·교체·삭제는 **`role === "admin"` 만** (`InviteManager` 와 같은 조건).
  관리자가 여러 명이어도 마지막 저장이 유효하다.
- 사용은 로그인한 교사 전원.

라우트
- `GET /api/ai/status` — `{groq, gemini}` **boolean 만** 반환. 키 값은 절대 반환하지 않는다.
- `PUT` · `DELETE /api/admin/ai-keys` — admin 만.
- `POST /api/ai/fill` — `{imageUrl}` 또는 `{text}`.
  응답은 JSON 스키마로 강제하고 **서버에서 zod 로 다시 검증한다.**

공급자
- 두 모드 모두 **Groq 우선, 실패 시 Gemini 폴백.**
- Groq 비전 모델은 프리뷰일 수 있다. **공식 문서(Images and Vision)에서 현재
  모델명을 확인**해 상수 한 곳에 두고 Gemini 폴백을 유지한다.
- 이미지 모드 우선순위는 **상수로 바꿀 수 있게** 하고, 실제 한국어 포스터 3~4장으로
  두 쪽 결과를 비교할 수 있게 한다.
- 이미지는 **Supabase 공개 URL 을 그대로 전달하는 방식을 우선 검토**한다
  (도메인 허용은 유지). base64 는 4MB 제한을 고려할 것.

오류는 원인별로 구분한다 (6종)
1. **키 미등록** — 컬럼이 `null`
2. **키 거부됨 (401·403)** — 공급자가 키를 거절. 폐기·오타·권한 문제
3. **한도 초과 (429)**
4. **모델 종료·없음 (404)**
5. **응답 형식 오류** — JSON 파싱 실패 또는 zod 재검증 실패
6. **이미지 주소·용량 거부** — 허용 도메인 아님 / 상한 초과

   `키 미등록` 과 `키 거부됨` 은 화면 문구를 나눈다.
   `AI_KEY_SECRET` 이 달라져 복호화가 안 되는 `키 읽기 실패` 는 또 다른 경우다.

   | 내부 상태 | 교사 화면 | AI 설정 팝업(admin) |
   |---|---|---|
   | 키 미등록 | "관리자가 AI를 설정하지 않았어요" | "키가 등록되지 않았습니다" |
   | 키 거부됨 | "AI 키가 거부됐어요. 관리자에게 알려 주세요" | "키를 다시 확인하세요" |
   | 키 읽기 실패 | "AI 키를 읽을 수 없습니다. 관리자에게 알려 주세요" | "키를 다시 등록해야 합니다" |

모델명
- 공급자별 상수 **한 곳**. **종료 임박 모델은 고르지 않는다.**

제한
- `imageUrl` 은 우리 Supabase 도메인만, 용량 상한
- `{text}` 는 8000자
- **교사별 시간당 20회** (`rateLimit.ts` 재사용)
- 요청 내용 로그 금지

화면
- **admin 에게만** 상단 메뉴에 "AI 설정" — Groq 키·Gemini 키 각각 입력·저장·삭제·상태.
- 교사 화면에는 **상태만.**
- 개인정보 안내 문구는 2026-10-03 에 확정했다. 교사 화면 두 곳과 관리자 팝업에 들어간다.
  **공급자 이름과 폴백 순서를 밝히므로 `PROVIDER_ORDER` 를 바꾸면 문구도 같이 고칠 것.**

### 실제 키로 확인한 결과 (2026-10-03)

문서가 아니라 **실제 호출로 확정했다.** 문서만 믿었으면 두 군데서 틀렸다.

- [x] **Gemini JSON 스키마 강제** — `POST /v1beta/models/<model>:generateContent` +
      `generationConfig.responseMimeType` + `responseSchema`. **이게 맞다.**
      문서가 보여주던 `/v1beta/interactions` + `response_format` 은 200 은 오지만
      우리가 요구한 항목이 하나도 담기지 않았다.
- [x] **이미지 전달** — 두 공급자 모두 **공개 URL 을 그대로** 받는다.
      Gemini 는 `file_data.file_uri`, Groq 은 `image_url.url`.
      base64 와 걸린 시간이 거의 같아서 URL 쪽을 쓴다 — 바이트가 우리 함수를
      거치지 않고 Supabase(서울)에서 바로 간다.
      Groq 은 base64 로 816KB 포스터를 보내자 **TPM 8000 한도에 걸려 429** 가 났다.
- [x] **용량 확인** — Supabase 는 HEAD 에 `content-length` 를 준다 (206 Range 도 됨).
      **아무 CDN 에나 통하는 방법이 아니다** — 같은 날 어떤 뉴스 CDN 은 HEAD 에 404,
      GET 에 200 을 줬다. 허용 도메인을 우리 Supabase 로 묶어 둔 것이 그래서 중요하다.
      크기를 알 수 없으면 거부한다(막는 쪽으로 실패).
- [x] **Groq 모델** — 문서의 Production 목록에 있던 `llama-3.3-70b-versatile` 는

## 완료: AI로 읽은 뒤 이미지를 바꾸거나 지웠을 때의 안내 (12단계 C, 2026-10-03)

AI 로 채운 뒤 대표 이미지를 다른 사진으로 바꾸거나 지워도, 이미 채워진 제목·본문·
활동 정보는 그대로 남는다. **엉뚱한 안내문의 정보가 붙은 글이 만들어질 수 있다.**

### 방침
- **자동으로 다시 부르지 않는다.** 이미지를 바꿨다고 AI 를 다시 호출하면
  "버튼을 눌러야만 전송한다" 는 원칙이 깨진다. 교사가 모르는 사이에 새 사진이
  AI 로 간다.
- **자동으로 지우지도 않는다.** 교사가 고쳐 둔 값이 사라지면 더 나쁘다.
- 대신 **카드 상태 줄에 주황색 안내**를 띄우고 버튼 두 개를 준다.
  - `[새 이미지로 다시 읽기]` — 기존 재실행 경로를 그대로 쓴다
  - `[AI가 채운 내용 지우기]` — **AI 가 채웠고 사용자가 아직 안 고친 값만** 지운다
- **붙여넣은 글을 고쳤을 때는 안내하지 않는다.** 글은 교사가 직접 다루는 것이라
  매번 띄우면 성가시다. 이미지만 대상으로 한다.
- **수정 화면(`PostDetail`)은 제외.** 거기에는 AI 카드 자체가 없다.

### 선행 확인 (2026-10-03) — 예측이 하나 틀렸다

- **대표 이미지 줄의 "바꾸기" 와 AI 카드의 이미지는 같은 값이다.** 둘 다
  `CreatePostDialog` 의 `thumbnailUrl` 한 상태에 묶여 있다. 맞다.
- **AI 가 넣은 본문 글상자는 이미 추적하고 있었다.** `aiBody = { id, text }`,
  `b.id === aiBody.id && b.value === aiBody.text` 일 때만 "안 고친 것". 활동 칸은
  `aiFilled`, 제목은 `aiTitleFilled`. 세 기준 모두 그대로 썼다.
- ~~"새로 들 상태는 읽은 이미지 주소 하나뿐"~~ — **틀렸다. 셋이 필요했다.**
  - `aiReadImage` — 읽은 주소. 예측한 그것
  - `aiImageNotice` — 두 입구가 **같은** state 를 쓴다는 사실이 오히려 문제였다.
    "사진이 달라졌는가" 로는 **누가 바꿨는지 구분할 수 없다.** 대표 이미지에서
    썸네일만 고른 교사가 자기가 건드리지 않은 것을 경고받게 된다. 그래서 안내는
    AI 카드 쪽 경로에서만 세운다
  - `aiEnabledApply` — 신청 받기를 AI 가 켰는지. `applyAiDates` 는 활동 칸이
    채워지면 토글을 무조건 켜서, 사용자가 미리 켠 경우와 구분이 없었다

### 결과
- 교체: 주황 안내 + `[새 이미지로 다시 읽기]` `[AI가 채운 내용 지우기]`
- 삭제: 주황 안내 + `[AI가 채운 내용 지우기]`
- 교체하면 상태 줄이 "올렸어요 · 아직 분석하지 않았어요" 로 돌아간다. 카드 안의
  `analyzed` 플래그를 없애고 `imageUrl === readImageUrl` 로 맞춰 본다 — 어긋날
  수 있는 상태를 하나 줄였다
- 안내는 다시 읽기 **성공**, 지우기, ×, 지울 내용이 없을 때 사라진다. 실패는 유지
- 지우기 규칙은 `clearAiFields` 순수 함수. 잘못 지우면 교사가 쓴 내용이 돌아오지
  않으므로 시험할 수 있어야 한다

### 안 한 것
- 수정 화면에 AI 카드 추가 (별개 과제)
- 이미지를 바꿀 때마다 확인 창 — 안내 한 줄로 충분했다

## 보류: 시각 없는 기간 행사 (전시·체험 주간) — **지금은 구현하지 않는다**

"과학주간 전시 11월 3일~7일" 처럼 **날짜만 있고 시각이 아예 없는** 행사가 있다.
지금은 시작 시각이 필수라, 교사가 아무 시각이나 넣게 된다.

### 왜 기본값을 넣지 않는가
`09:00` 같은 기본값은 **접수 마감을 어긋나게 만든다.** 신청 마감을 비우면 활동
시작이 곧 마감이다(`shared/activity.ts` 의 `applyClosesAt`). 그러면 아무도 안 정한
`09:00` 이 마감이 되어, 전시가 저녁까지 열려 있는데 오전에 접수가 닫힌다.
교사는 자기가 넣지 않은 시각 때문에 그렇게 된 줄 모른다.

그래서 **시각은 비울 수 없게 두는 쪽이 낫다.** 틀린 값이 조용히 들어가는 것보다
칸을 채우라고 막는 게 안전하다. 마감 칩도 시작 시각이 없으면 눌리지 않는다.

### 필요해지면 검토할 것 — "종일" 체크박스
- 저장할 때 시작 `00:00`, 종료 `23:59` 로 넣는다
- 화면에는 시각 대신 **"종일"** 로 표시한다 (상세 페이지, 요약 줄, `.ics`)
- 마감 칩의 "당일" 은 종일일 때 `23:59` 를 쓴다

`00:00`/`23:59` 자체는 이미 쓰는 값이다 — AI 가 시각 없는 신청 기간을 그렇게
채운다(`server/aiProviders.ts` 의 지시문). 같은 규칙을 활동 일시로 넓히는 일이다.

### 지금 하지 않는 이유
실제로 그런 글을 올리려다 막힌 적이 아직 없다. 요구가 생기면 그때 만든다.
화면에 체크박스를 하나 더 얹는 일이라 되돌리기도 쉽다.

## 보류: 일시 없는 접수형 글 (공모전·제출형) — **구현하지 않는다**

### 방침 (2026-10-03 결정)
**활동 신청은 우리 사이트에서 접수하는 활동에만 쓴다.** 공모전처럼 접수가 외부
(구글 폼·이메일·방문 제출)인 글은 **"신청 받기" 를 켜지 않고 본문에만 적는다.**
링크는 본문 글상자에 넣으면 자동으로 링크가 된다.

그래서 `shared/schema.ts` 의 "신청을 받으려면 활동 일시를 입력해야 합니다" 는
**고치지 않는다.** 아래는 나중에 방침이 바뀔 때를 위해 남기는 조사 결과다.

### 왜 간단하지 않은가
`eventStart` 가 "항상 있다" 는 전제가 **파일 8개에 퍼져 있다.** 한 곳만 고치면
조용히 어긋난다. 특히 `script/cleanup.ts` 는 개인정보 삭제 약속을 지키는 코드다.

| 파일 | 바꿔야 할 것 | 위험 |
|---|---|---|
| `script/cleanup.ts` | 기준을 `coalesce(event_end, event_start, apply_deadline)` 로 | **최고.** 빠뜨리면 접수형 글의 신청이 **영구 보존**된다. 방침·고지 위반 |

## 이미지 정리 도구 (설계만. **아직 만들지 않는다**)

버킷에 참조되지 않는 파일이 쌓인다. 파일을 고르는 즉시 업로드하는 구조라,
다른 사진으로 바꾸거나 글쓰기를 취소하면 그 파일이 그대로 남는다
(2026-07-25 조사: `post-images` 5개 중 4개가 미참조였다).

**자동 정리는 하지 않는다.** 지우면 되돌릴 수 없고, 참조 검사가 한 군데라도
어긋나면 살아 있는 글의 이미지가 사라진다. admin 이 눈으로 보고 고르게 한다.

### 화면
- admin 전용 "이미지 정리" 팝업. `AiSettings` 와 같은 조건으로 띄운다
  (`(!user || user.role === "admin")`), `createPortal` + `AnimatePresence` 밖.
- 목록에 파일 이름·용량·올린 시각·미리보기. 기본은 **아무것도 선택되지 않은 상태**.
- 고른 것만 지운다. 삭제 전 확인 한 번.

### 참조 검사 — 한 곳이라도 빠지면 살아 있는 이미지를 지운다
- `posts.image_url`
- `posts.blocks[].imageUrl`
- **`posts.blocks[].content` 가 스토리지 URL 인 경우** — 예전 글은 이미지 주소를
  글 칸에 넣어 둔 것이 있다. `shared/postBlocks.ts` 의 `renderBlock` 이 그걸
  이미지로 그린다. 빠뜨리면 보이는 이미지를 지우게 된다
- `popups.image_url`

### 대상 폴더
- `post-images`, `scraped`
- **`scraped` 는 뉴스 이미지 미러링 캐시다.** URL 이 DB 가 아니라 메모리 캐시에만
  있어서 DB 기준으로는 전부 미참조로 잡힌다. 지워도 다음 스크래핑에서 다시
  올라오지만 그동안 이미지가 깨져 보인다. **목록에서 경고를 달고 기본 선택에서 뺀다.**

### 안전장치
- **최근 24시간 이내 업로드는 목록에서 제외.** 지금 글을 쓰는 중인 파일을
  지우는 것을 막는다 (업로드가 저장보다 먼저 일어나는 구조라 반드시 필요하다)
- **삭제 직전에 서버가 참조를 다시 검사한다.** 목록을 띄워 둔 사이에 누군가
  그 이미지를 쓰는 글을 저장했을 수 있다. 목록을 만들 때의 판단을 믿지 않는다
- 지운 결과를 건수와 용량으로 보고

### 같이 고칠 것 — `storage-usage` 의 1000개 한계
`server/routes.ts` 의 `/api/storage-usage` 가 폴더당 `limit: 1000` 으로 한 번만
부른다. 파일이 1000개를 넘으면 **사용량이 조용히 적게 나온다.** 페이지를 끝까지
돌도록 고친다 (`offset` 을 옮기며 빈 쪽이 올 때까지). 정리 도구의 목록도 같은
방식이어야 한다.

### 안 하는 것
- 자동 정리·예약 삭제. keep-alive 워크플로에 붙이지 않는다
- 업로드 시점을 저장 직전으로 옮기는 것은 **별개 과제**다 (아래 "이미지 · Storage").
  그걸 먼저 하면 새로 쌓이는 것은 막히지만, 이미 쌓인 것은 그대로다

  조회 요청 제한이 **함께** 있어야 한다.)
