## 2026-07-28 — 하루 정리

### 배포한 것
3·4단계(학생 신청, 교사 명단)를 시작으로 1단계까지 닫았다. 순서대로:

1. 학생 신청 + 요청 제한 (`rate_limits` 테이블 신설, `db:push`)
2. 교사용 신청자 명단 + 엑셀 내려받기
3. 확인 수단을 6자리 랜덤 코드 → 학생 지정 비밀번호로 교체
4. 신청 기록 30일 자동 삭제 (`script/cleanup.ts`)
5. 교사 초대 링크 흐름, 아이디 로그인, 관리자용 비밀번호 재설정
6. `x-admin-password` 제거 — **1단계 완료**, 코드 455줄 감소
7. 활동을 폰 캘린더에 담기 (아이폰·안드로이드·태블릿)
8. keep-alive 워크플로 수리
9. 메뉴 "활동 일정" → "활동 신청" + 신청 가능 건수 배지
10. 개인정보처리방침 페이지

### 오늘 배운 것 세 가지
같은 실수를 반복하지 않으려고 따로 적는다.

**1. 응답 코드는 배포 성공의 증거가 아니다.**
`vercel.json` 에 `regions` 를 넣어 빌드가 거부됐는데, 사이트는 옛 배포본으로
멀쩡히 돌아가고 API 도 200 을 줬다. 두 커밋이 배포되지 않은 채로 "배포했다" 고
말했다. **번들 해시가 바뀌었는지 봐야 한다.**

**2. 증상을 기기로 묶으면 브라우저 차이를 놓친다.**
"아이패드는 캘린더가 안 열린다" 로 결론내고 응답 헤더를 고쳤는데, 실제로는
아이패드 **크롬**만 그랬고 사파리는 처음부터 잘 됐다. 헤더 변경은 헛수고였고
되돌렸다. 같은 기기에서 브라우저를 바꿔 보는 것이 확인 목록에 있어야 한다.

**3. 화면 문제라고 CSS 부터 만지지 않는다.**
초대 모달이 네비 바 안에 갇힌 것은 `.glass-nav` 의 `backdrop-blur` 가
자손 `fixed` 의 기준을 바꾸기 때문이었다. `max-h` 를 두 번 헛짚었다.
`PopupManager` 에 이미 같은 회피책(포털)이 있었는데 그 이유를 못 읽었다.
**기존 코드의 우회책에는 이유가 있다.**

### 검증 방식
기능마다 로컬 dev 서버에 실제 요청을 보내는 임시 스크립트로 확인하고 지웠다.

임시 스크립트는 `script/_tmp_*` 로 만들고 끝나면 지웠다. 검증용 DB 데이터도
매번 정리했고, 마지막에 실제 게시물·계정만 남은 것을 확인했다.

## 2026-07-28 — 개인정보처리방침 페이지, 데이터 위치 확인

### 데이터가 어디 있는지 먼저 확정했다
방침을 쓰려면 "국외 이전이 있는가"를 답해야 하는데, 그게 TODO 에 미확인으로 남아 있었다.

- **Supabase DB 는 서울이다.** `DATABASE_URL` 호스트가
  `aws-1-ap-northeast-2.pooler.supabase.com` — `ap-northeast-2` = 서울.
  오래 걸려 있던 "리전 확인" 항목이 이걸로 해결됐다. 저장은 국내다.
- **그런데 Vercel 함수는 미국에서 돈다.** `vercel.json` 에 `regions` 가 없어
  기본값(`iad1`, 워싱턴)이었다. 저장은 서울인데 학생 이름·학년·반이 담긴 요청은
  미국 서버를 거치고 있었다.

### `vercel.json` 의 `regions` 는 Hobby 에서 배포를 **깨뜨린다**
`"regions": ["icn1"]` 을 넣고 배포한 뒤 `x-vercel-id` 를 12번 확인했는데 계속
`iad1` 이었다. 처음에는 "Hobby 에서는 무시되는구나" 로 결론내고 설정을 남겨 뒀다.

**틀렸다. 무시되는 게 아니라 빌드가 거부된다.**
다음 커밋(개인정보처리방침 페이지)을 올렸는데 배포본에 반영되지 않아서 알았다.
번들 해시가 `regions` 를 넣기 **전** 커밋 그대로였다 — 그 시점부터 배포가 멈춰 있었다.

**가장 위험한 종류의 실패다.** 사이트는 옛 배포본으로 멀쩡히 돌아가서
겉으로는 아무 문제가 없다. API 도 200 을 준다. 새 코드만 조용히 안 올라간다.
"배포했다" 고 말하기 전에 **번들이 실제로 바뀌었는지** 봐야 한다는 뜻이다.
`/api/...` 가 200 인 것은 배포 성공의 증거가 아니다.

또 하나, 처음에 `x-vercel-id` 가 `icn1::iad1::...` 인 것을 보고 "서울에서 실행됨" 으로
잘못 읽었다. **앞은 접속한 엣지, 뒤가 함수 실행 리전이다.**
문자열에 `icn1` 이 들어있는지만 본 것이 실수였다.

`regions` 는 제거했다. 서울로 바꾸려면 대시보드
(Settings → Functions → Function Region)에서 해야 한다.

### 방침은 구현과 일치해야 한다
문서만 있고 지키지 않으면 없는 것보다 나쁘다. `Privacy.tsx` 상단에 방침 항목과
그것을 실제로 담당하는 코드를 표로 짝지어 뒀다 — 수집 항목은 `applications` 테이블,
30일 삭제는 `script/cleanup.ts`, 해시 저장은 `applyPassword.ts`,
명단 접근 제한은 `loadOwnedActivity`, 조회 제한은 `lookupPerStudent`,
집계만 공개는 `summaryFor`. 방침을 고칠 때 짝이 되는 코드를 같이 보라는 뜻이다.

신청 폼의 짧은 고지에서 전문으로 가는 링크도 넣었다. 두 문구가 갈라지면 안 된다.

### 채우지 않은 항목은 눈에 띄게 했다
개인정보 보호책임자 이름·직위·연락처는 내가 지어낼 수 없는 값이다.
`CONTACT` 에 자리표시자를 두고, 하나라도 안 채워져 있으면 **페이지 상단에 노란 경고
상자**가 뜨게 했다. 빈 칸이 조용히 공개되는 것보다 낫다.

국외 이전 항목도 지금 사실대로 적었다 — 저장은 서울, 처리는 미국, 국내로 옮기는
중이라고. Vercel 리전을 바꾼 뒤 "국외 이전 없음" 으로 고치면 된다.
**아직 아닌 것을 아니라고 쓰지 않는다.**

### 검증
`/privacy` 200, 푸터·신청 폼 링크 연결, `npm run check`·`npm run build` 통과.
방침이 약속한 30일 삭제가 실제로 도는지 `cleanup.ts --dry-run` 으로 확인했다.

## 2026-07-28 — 메뉴를 "활동 일정" 에서 "활동 신청" 으로

### 왜
"일정" 은 보기만 하는 곳처럼 들리고 "신청" 은 할 일을 가리킨다.
옆에 지금 신청할 수 있는 활동 수를 붙이면 **메뉴만 보고도 새 활동이 열린 걸 알아챈다.**
학생이 사이트를 다시 들어올 이유가 생긴다.

### 어떻게 셌나
집계 API(`/api/applications/summary`)의 `isOpen` 을 센다. 게시물 목록을 쓰지 않은 이유는
본문·블록까지 실려 무거운데 여기서 필요한 건 숫자 하나뿐이기 때문이다.
`isOpen` 판정은 서버가 `shared/activity.ts` 로 하므로 카드의 "신청 받는 중" 배지와
같은 기준이다.

0 이면 배지를 감춘다. "0" 을 띄우면 신청할 게 있다는 착각을 준다.

일정 화면 제목도 "활동 신청" 으로 맞추고 같은 숫자를 문장으로 보여준다.
메뉴에서 3 을 보고 들어왔는데 제목이 다르면 같은 곳인지 헷갈린다.
두 숫자는 **같은 쿼리**에서 뽑아 어긋날 수 없게 했다.

주소는 `/schedule` 그대로 뒀다. 이미 나간 링크가 깨지면 안 된다.

### 검증
활동을 만들고 지우며 숫자를 확인했다 — 신청 받는 활동 2건 추가 시 +2,
마감·신청 예정·종료·신청 안 받는 글은 세지 않음, 마감시키면 -1.
집계 목록에 `applyEnabled` 가 false 인 글은 아예 안 들어가는 것도 확인했다.

## 2026-07-28 — keep-alive 워크플로 손보기

### 왜 중요한가
잠들기가 **두 겹**이다. 하나만 막아서는 소용이 없다.

1. Supabase 무료 플랜은 **7일간 DB 요청이 없으면 프로젝트를 일시정지**한다.
   그러면 사이트 전체가 죽는다.
2. GitHub 은 **저장소가 60일간 조용하면 예약 워크플로를 끈다.**
   그러면 1번 방어가 통째로 사라진다. 빈 커밋이 그걸 막고 있었다.

방학처럼 아무도 손대지 않는 기간이 이 장치의 존재 이유다.

### 고친 것
- **주기 3일 → 2일.** 한계가 7일인데 3일 간격이면 두 번 연속 실패할 때 9일이 되어
  이미 늦다. 2일이면 두 번 실패해도 6일이라 여유가 있다.
- **단계 순서를 뒤집었다.** Supabase 핑이 맨 앞에 있어서, 핑이 한 번 실패하면
  그 뒤의 정리·빈 커밋이 **전부 실행되지 않았다.** 일시적인 장애가 keep-alive 자체를
  멈추는 구조였다. 핑을 맨 뒤로 보냈다 — 실패하면 빨간색으로 눈에 띄되
  앞 단계는 이미 끝난 뒤다.
- **빈 커밋에 `[skip ci]` 추가.** 이 커밋 때문에 Vercel 이 2일마다 재배포하고 있었다.
  Vercel 은 커밋 메시지에 이 표시가 있으면 빌드를 건너뛴다.
  (TODO 에 "빈 커밋 푸시 제거" 가 있었지만 **지우면 안 된다** — GitHub 의 60일
  규칙을 막는 장치다. 재배포만 없애는 것이 맞다.)
- **시크릿이 없으면 경고를 남긴다.** `::warning::` 으로 찍어서 실행 목록에서 보이게 했다.
  조용히 건너뛰면 학생에게 고지한 30일 삭제가 동작하지 않는 걸 아무도 모른다.
- 핑도 시크릿이 없으면 실패 대신 경고로 넘어간다.

### 정리 단계가 keep-alive 역할도 한다
`script/cleanup.ts` 는 `DATABASE_URL` 로 Postgres 에 직접 붙는다. REST 핑과 달리
DB 를 실제로 건드리므로 이것만으로도 일시정지를 막는다. 핑은 이제 이중 안전장치다.

### 확인
`gh` CLI 가 없어서 실제 실행 이력과 시크릿 등록 여부는 확인하지 못했다.
YAML 은 파싱해서 단계 순서·조건·`[skip ci]` 포함을 검증했다.
**`DATABASE_URL` 시크릿 등록은 사용자가 직접 해야 한다.**

## 2026-07-28 — 5단계 일부: 활동을 폰 캘린더에 담기 (.ics)

### 무엇을 만들었나
- `server/calendar.ts` — iCalendar 생성
- `GET /api/posts/:id/calendar.ics` — 활동 하나짜리 .ics (공개 경로)
- 신청 완료 화면과 활동 상세에 "내 캘린더에 추가" 버튼

### 알림의 정체
**우리가 알림을 보내지 않는다.** 파일 안의 `VALARM` 이 "시작 1일 전에 알려달라"는
표시이고, 담긴 뒤로는 **폰 캘린더가 스스로 울린다.** 서버는 관여하지 않고
인터넷이 끊겨 있어도 울린다. 학생이 직접 입력할 일정을 미리 채워주는 것에 가깝다.

그래서 한계가 분명하다. **아무것도 하지 않은 학생에게는 보낼 수 없다.**
버튼을 눌러 캘린더에 담아야 하고, 담았는지 우리는 알 수 없다.
푸시보다 약하지만 iOS 웹푸시는 홈 화면 추가 시에만 동작해서 절반이 못 받는다.

알림은 하루 전(`-P1D`)과 한 시간 전(`-PT1H`) 두 개를 넣었다. 활동이 내일 이내면
하루 전 시각이 이미 지나가서 울리지 않으므로 짧은 쪽이 필요하다.

### TODO 순서를 바꿨다
TODO 5단계에는 전체 구독 피드(`/api/calendar.ics`)만 적혀 있었다.
그런데 구독은 **갱신 주기를 우리가 정할 수 없다** — 구글 캘린더는 외부 ICS 를
몇 시간~하루에 한 번 가져가고 조절이 안 된다. 급한 공지에 못 쓴다.
등록 절차도 번거로워서 안내 페이지가 먼저 필요하다.

학생이 실제로 원하는 것은 "내가 신청한 그 활동을 잊지 않기"다. 버튼 하나로 끝나고
설명이 필요 없다. 그래서 활동별 담기를 먼저 만들었다. 구독 피드는 같은
`buildCalendar()` 를 쓰므로 나중에 붙이는 비용이 작다.

### 형식 규칙이 까다롭다
RFC 5545 를 직접 다뤘다. 라이브러리를 넣지 않은 것은 이 정도 분량에 의존성을
늘릴 이유가 없어서다. 대신 규칙을 지켜야 한다.

- **줄 끝은 CRLF.** LF 만 쓰면 일부 캘린더가 파일을 통째로 거부한다.
- **한 줄 75옥텟.** 한글은 UTF-8 로 글자당 3바이트라 제목 몇 글자면 넘는다.
  넘으면 접어야 하고(다음 줄을 공백으로 시작), **글자 중간에서 자르면 안 된다.**
  바이트를 세면서 글자 단위로 끊는다.
- `\` `;` `,` 이스케이프, 줄바꿈은 리터럴 `\n` 두 글자로.
- `METHOD` 는 넣지 않았다. `METHOD:PUBLISH` 를 붙이면 일부 클라이언트가 초대장으로
  취급해 참석 여부를 묻는다.
- `UID` 를 활동 id 로 고정했다. 다시 담아도 새 일정이 생기지 않고 갱신된다.
- 시각은 UTC(`...Z`)로 낸다. DB 가 UTC 를 담고 있어 변환이 필요 없고 `VTIMEZONE` 도
  안 넣어도 된다.
- 링크는 `DESCRIPTION` 과 `URL` 양쪽에 넣었다. 긴 URL 은 접히는데, 접힌 줄을
  제대로 풀지 못하는 클라이언트가 있어 `URL` 속성이 더 안전하다.
- 한글 파일명은 헤더에 그대로 못 넣는다(헤더는 latin1). RFC 5987 의 `filename*` 로
  UTF-8 을 싣고 ASCII 이름을 함께 준다.

### 클라이언트는 평범한 `<a href>` 로
fetch 로 받아 Blob 을 만들지 않았다. iOS 사파리가 `text/calendar` 응답을 캘린더
앱에 넘기도록 하려면 직접 이동이 낫다.

### 검증
28개 케이스 통과. 헤더(Content-Type·Disposition·`filename*`·latin1 범위),
형식(CRLF·75옥텟·접기 후 복원·깨진 문자 없음), 이스케이프 3종,
시각·UID·알림 2개·`METHOD` 없음, 개인정보(신청자 정보 0건),
종료 시각 없을 때 1시간 채움, 일시 없으면 400 / 없는 글 404.

**폰에서 실제로 캘린더 앱이 받아 알림이 울리는지는 여기서 확인할 수 없다.**
파일이 유효하고 헤더가 맞다는 것까지가 한계다. 기기 확인이 필요하다.

### 또 걸린 함정
`tsx` 는 서버 코드를 다시 읽지 않는다. `calendar.ts` 를 고치고 테스트를 돌려
28/28 이 나왔는데 **예전 코드를 검증한 것**이었다. 재시작하고 다시 돌렸다.
이미 DEVLOG 에 적어둔 함정에 또 걸렸다.

테스트 문자열의 역슬래시가 셸 heredoc·파이썬 패치를 거치며 계속 접혔다.
`\\,` 가 `\,` 로 변해 기대값이 "이스케이프 안 된 원문"을 찾고 있었다.
결국 `String.fromCharCode(92)` 로 만들어 해결했다.
**이스케이프를 검증하는 테스트는 소스에 역슬래시를 쓰지 말 것.**

### 안드로이드에서 다운로드만 됐다 (기기 확인으로 잡힘)
배포 후 안드로이드에서 눌러보니 캘린더가 열리지 않고 **파일이 다운로드**됐다.

원인은 크롬이 `text/calendar` 를 렌더할 수 없어서 무조건 내려받는 것.
`Content-Disposition` 을 `inline` 으로 바꿔도 달라지지 않는다. 학생이 다운로드
폴더에서 파일을 찾아 앱을 고르는 절차가 남으므로 실질적으로 안 쓰인다.

그래서 **구글 캘린더 TEMPLATE 주소**를 추가했다. 웹 링크라 캘린더 앱이 바로 열리며
일정이 미리 채워진다. `GET /api/posts/:id/calendar/google` 이 302 로 넘긴다.
주소를 클라이언트에서 만들지 않고 서버에서 만드는 이유는 설명 문구(마감·정원·링크)를
`postToEvent` 한 곳에서만 관리하기 위해서다.

**대가: 구글 TEMPLATE 주소에는 알림 항목이 없다.** 사용자의 기본 알림(보통 30분 전)이
적용되고 `.ics` 의 하루 전 알림은 사라진다. 학교 활동에서 30분 전은 거의 쓸모가 없어서,
안드로이드에서는 "저장 후 알림을 1일 전으로 바꾸세요" 안내를 함께 띄운다.

둘 중 하나를 없애지 않고 기기에 맞는 쪽을 먼저 보여준다. `navigator.userAgent` 의
`Android` 여부로 순서만 바꾸고, 다른 쪽도 작은 링크로 남긴다.
판별이 틀려도 학생이 다른 경로를 쓸 수 있어야 한다.

**이건 파일 검증으로는 절대 못 잡히는 종류였다.** 28개 케이스가 전부 통과했고
파일은 완벽하게 유효했다. 기기에서 눌러봐야 알 수 있었다.

### 검증 (구글 경로)
17개 케이스 통과. 302 목적지, `action=TEMPLATE`, 제목이 원문 그대로
(ICS 이스케이프가 섞이지 않음), `dates` UTC 구간, 장소·정원·마감(KST)·링크 전달,
개별 신청자 정보 0건, 종료 없을 때 1시간, 일시 없으면 400 / 없는 글 404,
그리고 `.ics` 경로의 알림 2개가 그대로 유지되는지.

### 안드로이드는 결국 인텐트여야 했다
구글 캘린더 웹 주소로 고쳤더니 이번에는 **앱이 아니라 브라우저에서** 열렸다.
`calendar.google.com` 은 구글 캘린더 안드로이드 앱이 딥링크로 받지 않는다.

그래서 `intent://` 로 바꿨다. 시스템의 "일정 추가"(`ACTION_INSERT`)를 직접 부르므로
구글 캘린더든 삼성 캘린더든 **기본 캘린더 앱이 열린다.**
`package` 를 못박지 않았다 — 구글 캘린더로 지정하면 삼성 캘린더만 쓰는 학생이 막힌다.

**서버 302 로는 쓸 수 없다.** 크롬이 리다이렉트를 통한 `intent://` 이동을 막는다.
사용자가 직접 누른 링크의 `href` 여야 해서 주소를 클라이언트가 만들어야 했다.
그러면 설명 문구가 서버·클라이언트로 갈라지므로, 이벤트 생성을
`shared/calendarEvent.ts` 로 옮겨 세 경로(.ics·구글·인텐트)가 같은 함수를 쓰게 했다.
`server/calendar.ts` 에는 .ics 직렬화와 구글 주소 변환만 남겼다.

인텐트 주소는 값에 세미콜론이 하나만 섞여도 파싱이 통째로 깨진다. 전부 인코딩하고,
인텐트를 못 받는 브라우저를 위해 `browser_fallback_url` 로 구글 웹 경로를 넣었다.

알림은 여전히 지정할 수 없다. 인텐트에도 구글 TEMPLATE 주소에도 해당 항목이 없다.
캘린더 앱 기본값이 붙으므로 안내 문구는 그대로 둔다.

### userAgent 판별을 믿으면 안 됐다
인텐트로 고친 뒤 안드로이드 **태블릿**에서 눌렀더니 여전히
"…ics 파일을 다시 다운로드 하시겠습니까?" 가 떴다.

원인은 태블릿 크롬이 화면이 크면 **"데스크톱 사이트"로 여는 것**. 그러면 userAgent 에
`Android` 가 없어서 판별이 빗나가고, 인텐트 대신 `.ics` 가 기본이 된다.
인텐트 링크는 아예 렌더되지도 않으므로 학생이 다른 방법을 고를 수조차 없었다.

**판별이 실패했을 때 막다른 길이 되는 구조가 문제였다.**
세 경로(인텐트·`.ics`·구글 웹)를 항상 보여주고 라벨에 기기를 적는다.
판별은 이제 **순서만** 정한다. 빗나가도 학생이 맞는 것을 고르면 된다.

기기별로 화면을 갈라야 할 때 참고할 것 — userAgent 로 **감추지 말고 정렬만 할 것.**

그다음 폰 두 종류(아이폰·안드로이드)는 정상이고 **태블릿만** 다운로드가 떴다.
가설이 맞았다. 순서라도 맞추려고 판별에 터치 지원 여부를 더했다 —
`Android` 문자열이 없어도 터치가 되고 Windows·Macintosh·iOS·CrOS 가 아니면
안드로이드로 본다. 아이패드는 데스크톱 모드에서 `Macintosh` 로 위장하는데
그쪽은 `.ics` 가 맞는 경로이므로 제외 목록에 넣었다.

브라우저 없이 UA 문자열 12종으로 검증했다 (폰·태블릿 일반/데스크톱 모드·삼성 인터넷·
아이폰·아이패드 일반/위장·윈도우 일반/터치·맥·크롬북·터치 없는 리눅스).
**터치스크린 리눅스 데스크톱은 안드로이드로 잘못 볼 수 있다.** 그래도 `.ics` 가
한 번 더 눌러야 하는 자리에 남아 있어 막다른 길이 되지 않는다 — 이게 세 경로를
항상 노출해 둔 이유다.

### 아이패드는 헤더로 고칠 수 없었다 (시도 후 되돌림)
아이폰은 되는데 **아이패드만** `.ics` 가 다운로드로 갔다. 같은 사파리인데 다르다.
아이패드 사파리는 데스크톱급이라 첨부 파일을 다운로드 관리자로 보낸다.

`Content-Disposition` 을 `attachment` → `inline` 으로 바꿔 봤다.
"첨부파일로 받아라" 대신 "그 자리에서 처리해라"이니 캘린더로 넘어갈 여지를 줄 거라
기대했다. **효과가 없었다. 아이패드는 그대로 다운로드했다.**

아이폰이 확실히 동작하는 경로를 건드리는 변경이라, 얻는 것 없이 위험만 남으므로
`attachment` 로 되돌렸다. 되돌린 상태가 아이폰에서 확인된 상태다.

**아이패드·PC 에서 `.ics` 가 내려받아지는 것은 브라우저 동작이고 응답 헤더로 바꿀 수
없다.** 그쪽에서는 받은 파일을 눌러 캘린더에서 열거나 구글 캘린더 링크를 쓰면 된다.
PC 는 주 사용처가 아니므로 더 파지 않기로 했다.

### 경계선은 기기가 아니라 브라우저였다
"아이패드는 안 된다"고 정리했는데 틀렸다. **아이패드도 사파리에서는 캘린더로 넘어간다.**
안 되던 것은 아이패드 **크롬**이었다. iOS 크롬은 자체 다운로드 관리자를 써서
`.ics` 를 파일로 받는다.

그래서 `Content-Disposition` 을 아무리 만져도 소용이 없었다. 사파리는 이미 잘 되고
있었고, 크롬은 헤더와 무관하게 다운로드한다.

**증상을 기기로 묶어서 잘못 결론냈다.** 같은 기기에서 브라우저를 바꿔 보는 것이
확인 목록에 있어야 했다.

### 최종 배치 — 기기마다 되는 두 개만
세 경로를 항상 띄우던 것을 그만뒀다. 안드로이드 인텐트는 PC·아이폰에서 아무 일도
일어나지 않는 링크라 오히려 혼란스러웠다.

| 기기 | 큰 버튼 | 작은 링크 |
|---|---|---|
| 안드로이드 (폰·태블릿) | 캘린더 앱에 추가 (인텐트) | 구글 캘린더 |
| 아이폰·아이패드 | 내 캘린더에 추가 (`.ics`) | 구글 캘린더 |
| PC | 구글 캘린더 | 캘린더 파일 받기 (`.ics`) |

**구글 캘린더를 모든 기기에 공통으로 남긴 것이 핵심이다.** 판별이 빗나가도 어디서든
되는 선택지가 하나 있으니 막다른 길이 없다. "감추면 막다른 길이 된다"와
"안 되는 링크를 띄우면 혼란스럽다"를 이걸로 동시에 만족시킨다.

PC 에서 `.ics` 를 완전히 없애지는 않았다. 맥은 파일을 열면 캘린더가 바로 뜨고
윈도우도 Outlook 이 있으면 열린다. 첫 자리를 줄 이유가 없을 뿐이다.

판별은 UA 문자열 14종으로 검증했다 (안드로이드 폰·태블릿·데스크톱 모드·삼성 인터넷,
아이폰 사파리·크롬, 아이패드 사파리·크롬·Mac 위장, 맥·윈도우·터치 노트북·크롬북·리눅스).

안드로이드는 세 번 고쳤다 — `.ics` 다운로드 → 구글 웹(브라우저) → 인텐트(앱) → 배치 정리.

### 검증 (인텐트)
23개 케이스 통과. `intent://` 형식, `ACTION_INSERT`, 이벤트 타입,
`beginTime`/`endTime` 이 epoch ms, 폴백 주소, `package` 미지정,
**모든 조각이 `key=value` (세미콜론 누출 없음)**, 제목·장소·설명이 원문으로 복원,
개별 신청자 정보 0건, 그리고 세 경로가 같은 이벤트를 쓰는지.

### 남은 것
- 전체 구독 피드 `GET /api/calendar.ics` + 구독 방법 안내 페이지

## 2026-07-28 — `x-admin-password` 제거 (1단계 완료)

### 무엇을 없앴나
- `server/auth.ts` — `legacyAdmin`, `AuthUser.legacy`, 미사용 `requireTeacher`
- `client/src/contexts/admin.tsx` — localStorage 평문 비밀번호, `login()`, `useAdminPassword`
- `POST /api/admin/verify` — 이제 `GET /api/me` 가 대신한다
- 로그인 창의 "관리자 비밀번호로 로그인" 전환
- `.env.example` 의 `ADMIN_PASSWORD`
- 미사용 인증 의존성 5개와 각 `@types` (`script/build.ts` 번들 목록에서도)

### 왜
평문 비밀번호를 localStorage 에 두고 매 요청에 실어 보내던 구조다.
XSS 한 번에 새고, 만료가 없고, 모두가 같은 값을 써서 누가 무엇을 했는지 알 수 없었다.

기능적으로도 걸림돌이었다. 이 방식으로 들어오면 `profiles` 행이 없어
게시물 `authorId` 를 null 로 넣어야 했고, 그래서 담당 교사가 자기 활동 명단을
볼 수 없었다. 제거하니 `authorId` 가 항상 채워진다.

### 순서를 지켰다
로그인 안전망을 없애는 작업이라 **아이디·이메일 로그인이 실제로 되는 것을 확인한 뒤에**
제거했다. 반대 순서였으면 잠겼을 때 되돌릴 방법이 없다.

`logout()` 에는 `localStorage.removeItem("admin_pw")` 를 남겨 뒀다.
예전에 로그인한 브라우저에 값이 그대로 남아 있으므로 한동안 지워 주는 것이 낫다.

환경변수가 없을 때(`VITE_SUPABASE_*` 누락) 로그인 창이 조용히 실패하지 않도록
안내 문구를 넣었다. 예전에는 관리자 비밀번호가 안전망이었지만 이제 없다.

### 검증에서 배운 것
`/api/admin/verify` 가 404 인지 확인하려 했는데 dev 서버는 매칭 안 되는 경로에
SPA HTML(200)을 돌려준다. Vite 미들웨어의 폴백이다.
"404 인가" 대신 **"인증을 통과시키지 않는가"** 를 확인하도록 바꿨다.
없어진 API 경로를 dev 서버에서 상태 코드로 검증하려 하면 이 함정에 빠진다.

관리자 비밀번호를 몰라 토큰 경로를 검증할 수 없었는데, 초대로 임시 admin 계정을
만들어 그 토큰으로 확인했다. 검증이 막히면 검증할 수 있는 상태를 만들면 된다.

### 검증
19개 케이스 통과. 옛 헤더로 `/api/me`·`/api/teachers`·`/api/invites`·
`/api/admin/popups`·글 작성·이미지 업로드 전부 401, `/api/admin/verify` 인증 불가,
아이디 로그인 → `/api/me` 200(`legacy` 필드 없음, role admin),

임시 계정과 검증용 게시물은 지웠다.

## 2026-07-28 — 교사 로그인을 이메일에서 아이디로

### 왜
교사에게 이메일을 입력받는 것이 번거롭다는 요청. 학교에서 쓰는 계정이라
`kim` 같은 짧은 아이디가 맞다.

### Supabase Auth 는 이메일을 요구한다
비밀번호 로그인 provider 는 이메일(또는 전화번호)이 필수다. 그래서 아이디 뒤에
받을 수 없는 도메인을 붙여 내부 이메일로 쓴다. `kim` → `kim@msgb.invalid`.
교사는 이 주소를 볼 일이 없다.

`.invalid` 는 RFC 2606 이 이 목적으로 예약한 TLD 다. 누구도 소유할 수 없으므로
실수로 남의 주소가 되거나 메일이 외부로 나갈 일이 없다.
실제로 Supabase 가 이 도메인으로 계정 생성·로그인을 받아주는지 먼저 확인하고 진행했다.

### 대가와 그 대비
**메일을 받을 수 없으니 교사가 스스로 비밀번호를 재설정할 수 없다.**
CLAUDE.md 에 Supabase Auth 를 고른 이유로 "비밀번호 재설정" 이 적혀 있었으니
그 근거 하나를 포기하는 셈이다. 사용자에게 알리고 결정을 받았다.

그래서 **관리자용 재설정을 같은 작업에 넣었다.** 이게 없으면 비밀번호를 잊은 교사가
영구히 못 들어온다 — 없애려던 지원 부담이 더 나쁜 형태로 돌아온다.
`POST /api/teachers/:id/reset-password` 가 임시 비밀번호를 만들어 한 번만 돌려주고,
관리자가 당사자에게 직접 전달한다.

임시 비밀번호에서 `0/o`, `1/l/i` 를 뺐다. 구두로 전달하는 값이라
"영이야 오야" 문의가 그대로 발생한다.

### 기존 계정이 잠기지 않게
`toLoginEmail` 은 입력에 `@` 가 있으면 그대로 쓴다. 아이디 방식으로 바꾸기 전에
실제 이메일로 만든 계정(첫 관리자)이 계속 로그인할 수 있어야 한다.
이 예외가 없으면 바꾸는 순간 그 계정이 잠긴다.

### 대문자는 거부하지 않고 낮춘다
`acceptInviteSchema` 가 `checkTeacherId` 보다 먼저 `.toLowerCase()` 를 걸어서
`Kim` 은 거부되지 않고 `kim` 으로 저장된다. 의도한 관용이다 —
대소문자를 구분하면 "Kim 인지 kim 인지" 로그인 문의가 생긴다.

다만 입력 필드가 `Kim` 을 그대로 보여주면 실제 아이디와 어긋나므로,
`onChange` 에서 즉시 소문자로 낮춘다.

### 스키마 파일 제약이 또 걸렸다
`acceptInviteSchema` 가 `teacherId.ts` 를 필요로 하는데, 그걸 `schema.ts` 에 두면
drizzle-kit 이 죽는다 (앞선 `applyForms.ts` 와 같은 이유).
`shared/inviteForms.ts` 로 분리했다. **`schema.ts` 는 표 정의만 갖는다**는 규칙이
두 번째로 확인됐다.

### 검증에서 배운 것 (테스트 설계 실수)
처음 돌린 테스트가 12/23 으로 나왔는데 대부분 거짓 실패였다.

- 거부 케이스들이 **초대 토큰 하나를 공유**했다. `Kim` 이 통과해 토큰을 소모하자
  뒤 케이스가 전부 "이미 사용된 링크" 400 을 받아 **거짓 통과**했고, 정작 필요한
  검증은 하지 않았다. 케이스마다 새 토큰을 뽑도록 고쳤다.
- 재설정 후 그 교사의 기존 토큰으로 403 을 확인하려 했는데, 비밀번호 변경이

**공유 상태를 쓰는 거부 케이스는 서로를 가린다.** 한 번 통과하면 나머지가
"거부됨" 으로 보이지만 이유가 다르다.

## 2026-07-28 — 초대 모달이 네비 바에 갇혀 있던 문제

### 증상
초대 발급 창이 화면 상단에 붙어 제목과 닫기 버튼이 잘렸다.
고치는 과정에서 본문이 접혀 헤더만 남았고, 그다음엔 아무것도 안 떴다.

### 원인 1 — `backdrop-filter` 가 `fixed` 의 기준을 바꾼다
`client/src/index.css` 의 `.glass-nav` 에 `backdrop-blur-md` 가 있다.
`backdrop-filter` 가 걸린 요소는 자손 `position: fixed` 의 **컨테이닝 블록이 된다.**
뷰포트 기준이 아니게 되는 것이다.

`InviteManager` 를 그 `<header>` 안에 넣었으니 `fixed inset-0` 이 화면 전체가 아니라
**높이 80px 짜리 네비 바**를 덮고 있었다. 그래서 상단에 붙고 잘렸다.

`PopupManager` 가 이미 `createPortal(modal, document.body)` 를 쓰고 있었고
주석에 "z-index 문제 없음" 이라고 적혀 있었다. 같은 함정을 이미 한 번 밟은 흔적인데
그걸 보고도 이유를 파악하지 못했다. **헤더 안에 모달을 넣을 때는 포털이 필수다.**

### 원인 2 — 포털을 `AnimatePresence` 안에 넣으면 렌더되지 않는다
포털을 붙이고도 창이 아예 안 떴다. 이렇게 썼기 때문이다.

```
<AnimatePresence>{open && createPortal(...)}</AnimatePresence>   // 안 나온다
{createPortal(<AnimatePresence>{open && (...)}</AnimatePresence>, document.body)}  // 정상
```

`AnimatePresence` 는 자식으로 받은 포털을 렌더하지 못한다. `PopupManager` 는
포털을 밖에 두고 있는데 순서를 반대로 짰다.

### 원인을 찾은 방법
브라우저 콘솔을 볼 수 없어서 dev 서버 로그를 봤다. 버튼을 누른 시각마다
`GET /api/invites 304` 가 찍혀 있었다. `enabled: open` 이 걸린 쿼리가 나갔다는 것은
**`open` 이 true 로 바뀌었다는 뜻**이다. 클릭·상태는 정상이고 렌더만 안 되는 상황으로
범위가 좁혀졌고, 그때 포털 위치를 의심했다.

### 헛짚은 것
CSS 높이 계산 문제로 보고 두 번 고쳤다. `max-h` 를 줄이고, 오버레이 전체를
스크롤하게 바꾸고, 안쪽 `flex-1` 을 걷어냈다. 전부 관계없는 수정이라 되돌렸다.
`ApplyDialog` 까지 같이 건드렸는데 그쪽은 네비 바 안이 아니라 애초에 문제가 없었다.

**증상이 "위치가 이상하다" 인데 원인이 레이아웃 계산이 아닐 수 있다.**
`fixed` 가 예상과 다르게 놓이면 CSS 값을 만지기 전에 조상에
`transform` / `filter` / `backdrop-filter` / `perspective` / `contain` 이 있는지 볼 것.

### 함께 개선한 것
발급 직후 링크 복사가 작은 글자 링크로 경고문 사이에 끼어 있었다. 그 화면에서 할 일은
복사 하나뿐이라 전체 너비 버튼으로 키우고, 복사하면 초록색으로 바뀌게 했다.
발급 직후에는 입력폼과 목록을 감춰 한 번뿐인 링크만 보이게 했다.

## 2026-07-27 — 1단계 마무리: 교사 초대 흐름

### 한 일
- `profiles` 에 첫 계정 삽입 — `skywind99@naver.com` 을 `admin` 으로 (이름은 "관리자")
- `server/invites.ts` 신설 — 토큰 발급·검증·수락
- `GET`/`POST /api/invites`, `DELETE /api/invites/:id` (admin 전용),
  `POST /api/invites/check`, `POST /api/invites/accept` (공개)
- `InviteManager.tsx` — 상단 툴바의 초대 발급 창 (admin 만 보인다)
- `AcceptInvite.tsx` — `/invite/:token` 계정 만들기 화면

### 계정이 하나도 없어서 교사 로그인이 막혀 있었다
Vercel 환경변수는 이미 들어가 있어서 로그인 창에 이메일 항목이 **보이는** 상태였다.
`auth.users` 에 계정도 하나 있었다. 그런데 `profiles` 가 0행이라
`server/auth.ts` 의 `userFromToken` 이 그 계정을 거부하고 있었다.

"초대받지 않은 계정을 서버에서 한 번 더 막는 장치" 가 유일한 계정까지 막고 있던 셈이다.
설계대로 동작한 것이고, 부트스트랩용 첫 행을 넣어야 풀리는 상태였다.

### 자율 가입을 끈 상태에서 계정을 어떻게 만드나
브라우저에서 `supabase.auth.signUp` 을 부르는 것이 자연스럽지만, 대시보드의
"Allow new users to sign up" 을 끄면 그 호출이 실패한다. 그걸 켜 두면
초대 없이 누구나 계정을 만들 수 있으니 설계 결정에 어긋난다.

그래서 **서버가 `service_role` 키로 Admin API(`auth.admin.createUser`)를 쓴다.**
자율 가입이 꺼져 있어도 동작하고, 브라우저 경로만 막힌다.
테스트에서 두 가지를 같이 확인했다 — anon 키로 직접 `/auth/v1/signup` 은 거부되고,
초대로 만든 계정은 정상 로그인된다.

### 토큰은 sha256, 학생 비밀번호는 scrypt
초대 토큰은 `randomBytes(32)` 라 256비트 난수다. 사전·무차별 공격이 성립하지 않으므로
sha256 으로 해시하고 그 값으로 바로 조회한다. scrypt 를 쓰면 인덱스 조회가 안 되어
전체 행을 훑어야 한다.

학생 확인 비밀번호는 사정이 정반대다. 사람이 정하는 짧은 값이라 반드시 scrypt 여야 한다.
같은 "해시로 저장한다" 인데 이유와 알고리즘이 다르므로 양쪽에 주석을 달았다.

### 순서와 되돌리기
`invites.used_by` 가 `profiles.id` 를 참조하므로 초대를 먼저 소모할 수 없다.
계정 → `profiles` → 초대 소모 순으로 진행하고, 마지막에
`used_by is null` 조건이 붙은 UPDATE 로 원자적으로 가져간다.
같은 링크를 두 사람이 동시에 열어도 한 명만 통과한다.

중간에 실패하면 앞 단계를 되돌린다. 안 되돌리면 로그인은 되는데 `profiles` 가 없어
서버가 거부하는 유령 계정이 남는다 — 방금 겪은 그 상태다.

### 검증
30개 케이스 통과. 비로그인 401, 발급·목록에 토큰 해시 0건, 링크 확인(유효·엉뚱·만료),
8자 미만·잘못된 이메일 거부, 수락 201, 같은 링크 재사용 400,
만든 계정으로 Supabase 로그인 → `/api/me` 가 teacher 로 응답,
교사는 초대 발급·목록 403, 교사는 남의 활동 명단 403(관리자는 200),
anon 키 직접 가입 거부, 초대 삭제 204/404.

## 2026-07-27 — 확인코드를 학생 지정 비밀번호로 교체

### 왜 바꿨나
6자리 랜덤 코드를 학생이 외우기 어렵다는 지적이 나왔다. 실제로 그렇다.
코드는 신청 완료 화면에 한 번만 나오고, 잊으면 담당 교사를 찾아가야 한다.
교사 부담을 줄이려고 만든 설계가 다른 경로로 교사에게 돌아오는 셈이다.

CLAUDE.md 의 "확정된 설계 결정" 이라 먼저 확인을 받고 바꿨다.

### 바꾸기 전에 짚은 것
학생이 정하면 **랜덤보다 확실히 약해진다.** 그냥 두면 절반이 `1234`, `0000`,
생년월일을 쓴다. 게다가 이 맥락에서는 공격자가 대상을 정확히 안다 —
같은 반 친구의 학년·반·번호는 다 알고 있다. 랜덤 코드는 "누구 것인지 알아도
못 찍는" 상태였는데, `1234` 는 다섯 번 안에 들어간다.

그래서 "인증번호 **또는** 비밀번호" 처럼 둘 다 열어두는 방안은 접었다.
보안은 약한 쪽으로 결정된다. 코드가 아무리 강해도 `1234` 가 같이 걸려 있으면
그게 열쇠가 된다.

### 대신 넣은 것
`shared/studentSecret.ts` — 추측하기 쉬운 값을 거부한다.
- 4자 이상 20자 이하, 숫자만 쓸 때는 6자 이상
- 흔한 비밀번호 목록, 같은 문자 반복, 연속 증가·감소
- **생년월일 형태(YYMMDD·YYYYMMDD)** — 6자리를 정하라고 하면 대부분 생년월일을
  쓴다. 같은 학년이면 태어난 해가 거의 정해져 있어 실제로는 몇백 가지뿐이다
- 본인 학년·반·번호를 이어붙인 값

본인 번호만 거부한다. 모든 학번 형태를 막으면 정상 비밀번호가 대량으로 걸린다.

클라이언트와 서버가 같은 함수를 쓴다. 규칙이 갈라지면 화면은 통과인데 서버가
400 을 준다. 신청 폼은 입력 중에 사유를 보여주고, 서버는 접수 직전에 다시 검사한다.

**조회 화면에서는 강도 검사를 하지 않는다.** 규칙이 바뀌기 전에 만든 비밀번호로도
조회해야 하고, "이 값은 규칙에 안 맞음" 이라는 응답 자체가 추측 범위를 좁혀 준다.

### 24시간 잠금은 빼기로 했다
처음엔 실패 3회/시간 + 누적 10회 시 24시간 잠금을 제안했다. 사용자가 잠금을
거부했고, 그 판단이 맞다. 학교에서 하루 잠기면 학생이 결국 교사를 찾아가고
그게 이 설계로 피하려던 부담이다.

그래서 3단계와 같은 값을 유지했다 — **학생 단위 실패 5회 / 10분, 잠금 없음.**
맞히면 즉시 풀린다. 남은 강도 방어는 위의 비밀번호 규칙 하나뿐이므로
**규칙을 느슨하게 만들 때는 요청 제한도 함께 봐야 한다.** 주석에 적어 뒀다.

조회와 취소는 **같은 카운터**를 쓴다. 따로 걸면 느슨한 쪽에서 비밀번호를
알아낸 다음 다른 쪽으로 넘어가면 되므로 제한이 무의미해진다. 테스트로 확인했다.

### 남은 위험 (알고 두는 것)
마음먹은 같은 반 친구가 몇 번 찍어서 남의 신청을 취소할 확률이 0 은 아니다.
랜덤 코드였을 때보다 확실히 높다. 취소하면 행이 지워지므로 교사는 그 신청이
있었다는 사실조차 모른다. 문제가 실제로 생기면 취소를 "지우기" 대신
"교사에게 보이는 취소 표시" 로 바꾸는 것이 다음 수단이다.

### 화면
- 신청 폼에 "내 확인 비밀번호 정하기" 영역. 확인용 재입력까지 받는다.
  되돌려줄 방법이 없으므로 오타로 잠기는 일을 막아야 한다.
- **한글을 권한다.** "우리반최고" 같은 한국어 단어가 네 자리 숫자보다 훨씬 안전하고

- 완료 화면에서 코드 카드를 없앴다. 학생이 정한 값이라 다시 보여줄 필요가 없고,
  서버는 해시만 갖고 있어 보여줄 수도 없다.
- 비밀번호가 두 개라 이름을 갈랐다. **활동 비밀번호**(교사가 학급에 알려주는 것)와
  **확인 비밀번호**(학생이 정하는 것).

`applications.code_hash` 열 이름을 그대로 뒀다. 담기는 값은 학생이 정한

### db:push 가 죽었다 — schema.ts 는 상대 import 를 못 받는다
`shared/schema.ts` 에 `import ... from "./studentSecret.js"` 를 넣자

### 요청 제한을 메모리에 둘 수 없었다
확인코드는 6자리다. 100만 가지라 제한이 없으면 하루면 전교생 명단이 털린다.
그런데 서버리스에서 모듈 전역 변수는 인스턴스마다 따로 존재한다.
메모리 카운터를 쓰면 인스턴스가 늘어난 만큼 제한이 느슨해지고, 공격자는
요청을 빨리 보내기만 하면 된다. 이 프로젝트의 뉴스 캐시가 이미 그 상태다.

그래서 `rate_limits` 테이블에 고정 창 카운터를 둔다. `insert ... on conflict do update`
한 번으로 증가와 창 초기화를 함께 처리하고, 남은 시간까지 SQL 안에서 계산해서 돌려준다.
`window_start` 를 raw SQL 로 읽으면 드리즐의 UTC 매핑을 안 타서 시간대가 어긋난다.
계산을 SQL 밖으로 꺼내지 말 것.

**DB 오류가 나면 막는 쪽으로 넘어간다.** 요청 제한이 죽은 채로 신청·조회 API 가
열려 있는 것보다 잠깐 안 되는 게 낫다. 테이블이 없으면 이 동작 때문에 바로 드러난다.

### 학교는 한 반이 같은 IP 로 나온다
이게 설계를 크게 바꿨다. IP 기준으로 조이면 한 반이 수업 시간에 동시에 신청할 때
정상 사용자가 막힌다. 그래서:

- 신청은 IP 기준 10분 40회로 넉넉하게. 중복은 유니크 제약이 막으므로 여기서 조일 필요가 없다.
- 조회는 **학생 단위**(활동+학년+반+번호)가 주 방어선이다. 10분에 5회.
- **성공하면 카운터를 지운다.** 그래서 실질적으로 연속 실패만 쌓인다.
  이 초기화가 없으면 공용 IP 뒤의 학생들이 서로를 막는다.

10분에 5회면 100만 가지를 훑는 데 현실적으로 불가능한 시간이 걸린다.

### 정원 경합
정원을 세고 삽입하는 사이에 다른 요청이 끼어들면 정원을 넘겨 받는다.
트랜잭션만으로는 안 막힌다 — 아직 없는 행은 잠글 수 없다.
`pg_advisory_xact_lock(네임스페이스, post_id)` 로 같은 활동의 신청을 한 줄로 세웠다.

중복 검사도 유니크 제약에 맡기지 않고 락 안에서 미리 조회한다.
제약 위반으로 실패하면 트랜잭션이 중단 상태가 되어 뒤처리가 지저분해진다.
제약은 그대로 두되 안전망 역할만 한다.

### 취소는 지우고, 대기자는 자동으로 올린다
상태를 `cancelled` 로 남기면 유니크 제약 때문에 다시 신청할 수 없다.
취소한 학생 정보를 계속 들고 있을 이유도 없어서 행을 지운다.

빈 자리가 생기면 가장 먼저 대기한 학생을 신청 확정으로 올린다.
안 올리면 나중에 신청한 학생이 그 자리를 차지해 대기 순서가 뒤집힌다.
승격된 학생에게 알릴 방법은 없지만, 확인코드로 조회하면 바뀐 상태가 보인다.

### 화면과 서버가 같은 판정을 쓰게 했다

### 날짜가 JSON 을 건너지 못하던 문제
`insertPostSchema` 는 `createInsertSchema` 가 만든 것이라 timestamp 열이 `z.date()` 였다.
그런데 브라우저가 `JSON.stringify` 하는 순간 Date 는 문자열이 되므로,
활동 일시를 넣은 요청은 서버에서 전부 400 이 될 상태였다.

`z.preprocess` + `z.coerce.date()` 로 감싸 문자열·Date 둘 다 받게 했다.
빈 문자열을 `null` 로 먼저 바꾸는 것이 핵심이다. `datetime-local` 입력을 비우면
`""` 가 오는데, `coerce.date("")` 는 Invalid Date 가 되어 "날짜 형식이 올바르지 않습니다" 로
막힌다. 사용자는 그냥 입력을 안 한 것인데 에러가 나는 셈이다. 정원(`capacity`) 도 같다.

시간대는 검증했다. `datetime-local` → `new Date()` (지역 시간 해석) → `toISOString()` (UTC)
→ Drizzle `timestamp without time zone` 저장 → 읽을 때 UTC 로 해석.
왕복해도 어긋나지 않는다. `05:00Z` 를 넣으면 화면에 `14:00` 으로 나온다.

### 검증 스키마를 하나로 모은 이유
`createPostSchema` 는 `.refine()` 체인이라 `.partial()` 을 붙일 수 없다 (ZodEffects 가 된다).
그래서 `checkActivityDates()` 라는 함수로 refine 묶음을 빼내고,
`insertPostSchema` → 생성용 / `.partial()` → 수정용에 각각 적용했다.
refine 조건은 값이 없는 필드를 통과시키도록 썼기 때문에 부분 수정에도 그대로 쓸 수 있다.

같은 스키마를 클라이언트에서도 저장 직전에 `safeParse` 로 한 번 돌린다.
서버가 400 을 주기 전에 같은 문구를 토스트로 보여주기 위한 것이고, 규칙이 갈라지지 않는다.

### 신청 비밀번호 해시가 공개로 새고 있었다
`GET /api/posts` 는 `db.select()` 결과를 그대로 `res.json()` 하고 있었다.
`applyPasswordHash` 열을 추가한 순간부터 로그인 없이 전교 활동의 해시를 긁을 수 있는 상태가 된다.
신청 비밀번호는 교사가 학급에 구두로 알려주는 짧은 문자열이라 오프라인 대입이 현실적으로 가능하다.

`toPublicPost()` 로 해시를 떼고 `hasApplyPassword` 불리언만 내려보낸다.
게시물을 반환하는 네 경로(목록·상세·생성·수정) 전부 이 함수를 거친다.
수정 화면에서 필요한 건 "설정돼 있는가" 하나라서 잃는 기능이 없다.

해싱은 Node 내장 `scrypt` 를 썼다. bcrypt 를 새로 넣지 않았다 —
네이티브 빌드가 서버리스 번들에서 문제를 만들 수 있고, 이 용도에는 과하다.

### 비밀번호를 읽어올 수 없어서 생기는 문제
수정 화면은 기존 비밀번호를 표시할 수 없다 (해시만 있으므로).
그래서 "신청 비밀번호 사용" 토글과 입력란을 나눴다.
- 토글 끔 → 빈 문자열을 보내 서버가 해시를 `null` 로 지운다

서버의 `applyPassword === undefined` 분기가 이 세 경우를 가른다.

### 설계 결정
- **토큰 검증을 Supabase Auth 서버에 위임한다.** JWT 시크릿을 직접 다루지 않으므로
  키 형식이 바뀌거나 회전돼도 코드를 고칠 필요가 없다. 관리자 경로에서만 쓰이므로
  왕복 비용은 감수한다.
- **`profiles` 행이 없는 계정은 거부한다.** `auth.users` 에 계정이 있어도 통과하지 못한다.
  자율 가입을 열지 않는다는 원칙을 서버에서 한 번 더 막는 장치다.
- **환경변수가 없으면 교사 로그인만 비활성화된다.** `VITE_SUPABASE_*` 가 없으면
  `supabase` 가 null 이 되고 모달은 기존 화면과 동일해진다. 배포에 환경변수를
  깜빡해도 잠기지 않는다.

### 메모
- 브라우저에서 쓰는 값은 `VITE_` 접두사가 필요하다. Vite 는 그 접두사가 붙은 변수만
  클라이언트 번들에 넣는다. 값은 기존 `SUPABASE_URL`, `SUPABASE_ANON_KEY` 와 같다.
- `SUPABASE_SERVICE_KEY` 를 `VITE_` 로 만들면 DB 전체 권한이 공개된다. 절대 금지.
- Vite 환경변수는 시작 시점에 주입되므로 추가 후 dev 서버 재시작이 필요하다.

### 이미지 업로드 500 — 원인은 환경변수가 아니었다
증상은 `POST /api/upload-image 500 ... "Storage 업로드 실패. SUPABASE 환경변수를 확인하세요."`
그런데 환경변수는 처음부터 정상이었다. 응답이 6ms 였던 게 단서였다 —
Supabase 로 네트워크 요청이 아예 나가지 않았다는 뜻이다.

실제 원인은 `@supabase/supabase-js` 2.109 가 `createClient` 단계에서 RealtimeClient 를
초기화하면서 native WebSocket 전역을 요구하는 것. Node 22 부터 제공되므로 Node 20 에서는
예외가 났다. Storage 만 써도 클라이언트 생성에서 막힌다.
`realtime.transport` 로 `ws` 를 넘겨 해결. `ws` 는 이미 의존성이고 번들 allowlist 에도 있었다.

Node 22 로 올리면 `ws` 없이도 되지만 그대로 두기로 했다. Node 20/22/24 어디서든
동작해서 런타임이 바뀌어도 다시 볼 일이 없고, 잃는 것도 없다 (Realtime 자체를 안 쓴다).

### 왜 락파일이 문제였나
`package.json` 에는 `@supabase/supabase-js: ^2.108.2` 가 있는데
커밋된 `package-lock.json` 에는 그 항목이 아예 없었다.
그래서 새로 `npm install` 할 때마다 범위 내 최신으로 해석돼 2.109.0 이 들어왔다.
로컬(Node 20)에서만 터지고 배포(Node 24)에서는 안 터지던 이유가 이것이다.

### 삽질 기록
- 에러 메시지가 "SUPABASE 환경변수를 확인하세요" 라고 단정해서 환경변수를 한참 뒤졌다.
  실패 원인이 무엇이든 같은 문구를 반환하는 구조였다.
  `uploadBufferToStorage` 가 `null` 대신 `UploadResult` 를 반환하도록 바꿔
  환경변수 누락 / 클라이언트 생성 실패 / 업로드 거부를 구분한다.
  상세 원인은 서버 로그에만 남기고 응답에는 정리된 문구를 보낸다.
- `/api/storage-usage` 도 직접 `createClient` 를 부르고 있어 같은 버그가 있었다.
  공용 `createSupabaseClient` 헬퍼로 통일하고 중복 선언된 `BUCKET` 도 한 곳에서 export.

### 배포 후 겪은 것
푸시 후 `/api/posts`, `/api/popups` 가 500. `/api/science-news`(DB 미사용)는 200 이라
함수·번들 문제는 아니고 DB 접근만 실패하는 상황이었다.
원인은 Vercel 환경변수의 `DATABASE_URL`·`ADMIN_PASSWORD` 가 새 Supabase 프로젝트와
맞지 않았던 것. **환경변수 변경은 기존 배포에 적용되지 않는다** — 새 배포가 필요하다.

### 메모

## 2026-07-25 — 활동 신청 게시판 설계 결정

### 결정한 것
1. **학생 계정을 만들지 않는다.** 신청은 학년·반·번호·이름 + 6자리 확인코드.
2. **교사만 Supabase Auth 로 로그인한다.** 자율 가입 없음, 초대 링크로만 계정 생성.
3. **신청 기록은 활동 종료 30일 후 자동 삭제한다.**

### 왜 학생 계정을 포기했나
얻는 것은 본인 확인 하나인데, 딸려오는 것이 너무 많다.
비밀번호 재설정 문의, 졸업·전학생 계정 정리, 학생 개인정보 보관 책임,
그리고 "가입을 안 해서 신청을 못 했다"는 민원. 학교 실무에서 이건 전부 담당 교사 몫이 된다.

대신 세 가지로 보완하기로 했다.
- `(post_id, 학년, 반, 번호)` 유니크 제약 → 중복·장난 신청을 1인 1건으로 제한
- 교사가 명단을 최종 확정 → 이상한 신청은 지우면 끝
- 활동별 신청 비밀번호(선택) → 해당 학급에만 구두로 알려주면 사실상 그 반만 신청 가능

완벽한 본인 확인은 아니다. 마음먹으면 친구 이름으로 신청할 수 있다.
다만 이 규모에서는 교사 확인으로 충분히 걸러지고, 그 대가로 운영 부담이 거의 0이 된다.

### 검토했다가 뺀 것
- **나이스 연동** — 나이스가 외부에 개방하는 건 학교 기본정보·급식·학사일정 같은
  데이터 조회용 Open API다. 인증키를 받아 쓰는 방식이고, 학생·교사 계정을
  외부 사이트 로그인 수단으로 넘기는 SSO는 없다. 신원 확인에는 못 쓴다.
  급식·학사일정 표시 용도로는 나중에 쓸 수 있으니 "나중에" 목록에 남겨 뒀다.
- **구글 워크스페이스** — 학교 도메인 계정이 없어 해당 없음.
- **웹푸시** — iOS는 홈 화면에 추가해야만 동작해서 학생 절반이 못 받는다.
  ICS 캘린더 피드로 대체. 서버는 텍스트만 뱉으면 되고 알림은 폰이 알아서 울린다.

### 인증 방식 재검토
지난번엔 관리자 비밀번호 하나짜리라 JWT 직접 구현이 합리적이었다.
그런데 교사 여러 명 + 역할 구분 + 비밀번호 재설정 + 초대 흐름이 붙으니
직접 만들 코드가 몇 배로 늘어난다. 전부 Supabase Auth 에 이미 들어 있고
프로젝트가 이미 Supabase 를 쓰고 있으므로 직접 구현은 접었다.
Supabase Auth 도 내부적으로는 JWT라서, "세션이냐 JWT냐" 고민 자체가 사라졌다.
